# terraform-provider-plain

A Terraform provider for [Plain](https://www.plain.com), managing workspace
configuration through Plain's GraphQL API.

Module path: `github.com/jeremybumsted/terraform-provider-plain`
Registry address: `jeremybumsted/plain`

## Toolchain

Everything is managed by [mise](https://mise.jdx.dev). Do not install tools
globally or add a Makefile — add a `[tasks.*]` entry to `mise.toml` instead.

```
mise install          # provision Go, golangci-lint, goreleaser, terraform
mise run build        # build the provider binary
mise run test         # unit tests
mise run testacc      # acceptance tests — hits the real Plain API, needs PLAIN_API_KEY
mise run lint         # golangci-lint
mise run schema       # re-download graphql/schema.graphql from Plain
mise run generate     # regenerate the typed GraphQL client
mise run docs         # regenerate registry docs
mise run dev-override # write .terraformrc-dev for testing against a local build
mise tasks            # list everything
```

**Go-based tools go in the `tool` directive in `go.mod`, not in `[tools]`.**
genqlient and tfplugindocs are both invoked as `go tool <name>`. This is not
stylistic: genqlient v0.8.1 (the latest) pins `golang.org/x/tools` v0.24.0, which
does not compile under Go 1.26, so `go install github.com/Khan/genqlient@latest`
fails outright. As a module dependency we control that version — go.mod pins
`x/tools` v0.49.0 and genqlient builds fine. Do not "fix" this by downgrading Go
or by moving these back to mise's `go:` backend.

## Layout

```
main.go                       provider server entrypoint
plain/                        the whole provider — one package
  provider.go                 provider config and registration
  *_resource*.go              resource schema, CRUD, lifecycle
  *_acc_test.go               acceptance tests; need TF_ACC and a real workspace
  acc_test.go                 acceptance-test harness and API-level checks
  client.go, errors.go        authenticated GraphQL client
  generated.go                GENERATED by genqlient — never hand-edit
  graphql/schema.graphql      vendored copy of Plain's published schema
  graphql/operations/*.graphql  hand-written operations; genqlient reads these
examples/                     example config; tfplugindocs reads this
docs/                         GENERATED — never hand-edit
.docs/                        local reference notes, gitignored
```

Everything Go lives in one `plain` package. There is deliberately no `internal/`:
the provider is a binary, not a library, so the import barrier bought nothing and
cost a layer of nesting. Resources and the GraphQL client sharing a package means
no qualifier noise at call sites; keep the generated client in `generated.go` and
hand-written code in named files so the boundary stays obvious.

`.docs/` holds the long-form findings behind this file: API-wide conventions and
the workflow deep-dive. Start at `.docs/README.md`. It is gitignored — if
something there needs to be authoritative, promote it into this file.

## The Plain API

- Endpoint: `https://core-api.uk.plain.com/graphql/v1`
- Auth: `Authorization: Bearer <api key>`
- Schema is public and needs no auth:
  `https://core-api.uk.plain.com/graphql/v1/schema.graphql`
- API keys carry granular permissions. A 403 usually means a missing permission
  on the key, not a bad key — say so in the diagnostic.

**Mutations report business errors in the payload, not in the GraphQL `errors`
array.** Every mutation output is shaped `{ <entity>: T, error: MutationError }`,
where `MutationError` has `message`, `type`, `code`, and `fields`. A mutation can
return HTTP 200 with a null entity and a populated `error`. Every call site must
check `output.Error != nil` before using the result — a transport-level error
check alone will silently succeed on failure. Surface `error.code` in
diagnostics; codes are documented at
<https://www.plain.com/docs/graphql/error-codes>.

**core-api serves transient HTTP 500s in multi-minute windows.** The client
retries them (`plain/retry.go`), but only for the operations in `retryableOps`:
read queries, plus `deleteWorkflow` because Delete already treats `not_found` as
success. `createWorkflow`, `updateWorkflow` and `bulkUpsertWorkflowSteps` are
deliberately excluded — a lost 500 from a write may mean the write landed, so a
replay would duplicate a workflow or re-run a graph replace. Do not add them.

The retry lives in a `graphql.Client` wrapper rather than in `authTransport`,
because a `http.RoundTripper` sees only an `http.Request`: scoping there would
mean parsing the operation name back out of the JSON body and buffering that
body to make it replayable. At the GraphQL layer the operation name is a struct
field and genqlient marshals a fresh request per attempt, so replay is free. It
also means a payload error on an HTTP 200 is structurally unreachable from the
retry loop — genqlient returns a nil error for those.

Four attempts, full-jitter backoff, and the whole sequence is bounded by
`clientTimeout` (60s) via a context deadline, so a retrying call takes no longer
in the worst case than a single non-retrying one did. When the next backoff
would not fit in the remaining budget the sequence is abandoned and the
underlying 5xx is returned, not a deadline error.

## Scope

**Workflows only.** Plain's schema exposes 777 mutations covering threads,
customers, help centers, integrations and more. None of that is in scope. Do not
add resources for it, and do not propose it — if the scope widens, that will be
an explicit decision.

Most of the API is runtime support data (threads, customers, notes, tasks,
broadcasts) which must never go into Terraform state regardless.

### The workflow surface

| Resource | Status | Mutations | Read |
|---|---|---|---|
| `plain_workflow` | implemented | `createWorkflow` / `updateWorkflow` / `deleteWorkflow` / `bulkUpsertWorkflowSteps` | `workflow` |

**`WorkflowRule` is out of scope — deprecated by Plain.** It is a separate, flat
concept that happens to share the name: a named JSON payload with no steps and
no graph, Plain's older automation model. The provider had a
`plain_workflow_rule` resource and it has been removed. Plain still exposes
`createWorkflowRule` / `updateWorkflowRule` / `toggleWorkflowRulePublished` /
`deleteWorkflowRule` and the `workflowRule`/`workflowRules` queries, but the
feature is no longer supported — the surviving GraphQL is not a reason to bring
the resource back. Do not re-add it.

**Design decision: `plain_workflow` owns its whole step graph.** Plain models
steps as separately-addressable entities (`createWorkflowStep`,
`updateWorkflowStep`, `deleteWorkflowStep`), but exposing them as a standalone
`plain_workflow_step` resource would force practitioners to hand-wire step IDs
through `transitions` arrays — a graph of mutually-referencing resources that
Terraform cannot order correctly and that breaks on any restructure.

Use `bulkUpsertWorkflowSteps` instead. It atomically replaces the entire step
list (matching IDs update, new ones create, absent ones delete) and sets
`startStepId` and `trigger` in the same call. So `plain_workflow` carries its
steps as a nested block and reconciles the whole graph in one mutation. There is
no `plain_workflow_step` resource.

**Steps are a map keyed by a local name, not a list.** Config cannot reference
Plain's step IDs — they do not exist until after create. So `steps` is a
`MapNestedAttribute` whose key is a practitioner-chosen handle, and `start_step`,
`next`, `on_true` and `on_false` refer to those keys. The provider resolves keys
to IDs on write and back to keys on read. A map (rather than a list) makes key
uniqueness structural and reordering a non-event.

Consequence for import: Plain does not store the keys, so imported steps are
keyed by their Plain step ID. That is documented in the import example.

Things the implementation gets right, and must keep getting right:

- **`trigger` and step `payload` are JSON-encoded strings**, not typed fields.
  Normalize them (stable key order) before storing in state or every plan will
  show spurious drift. Consider `jsontypes.Normalized` from
  `terraform-plugin-framework-jsontypes`.
- **Publishing is a lifecycle state, not just a flag.** `publishedAt == null`
  means draft. `startStepId` cannot be cleared on a published workflow — to
  restructure, `updateWorkflow{isPublished: false}` → restructure → republish.
  Update sequences this itself, inside one apply. `graphChanged` decides when:
  it treats added/removed/retyped/rewired steps as structural but deliberately
  ignores payload edits, so a routine payload tweak never takes live automation
  offline. Verified against a real workspace — a payload edit does not
  unpublish, a branch swap does. Do not widen `graphChanged` to cover payloads.
- **Step payloads embed workspace-specific IDs** (label type IDs, user IDs, tier
  IDs). They are not portable across workspaces. Examples must build payloads
  from references to other resources/data sources, never from copy-pasted IDs.
- **`transitions` is positional**: ACTION steps have 1 element (next), CONDITION
  steps have 2 (true branch, false branch). `null` means terminal.
- Step `positionX`/`positionY` are canvas coordinates. They are cosmetic but
  required on create; default them rather than making practitioners supply them.
- **Step IDs are minted client-side.** `bulkUpsertWorkflowSteps` honours a
  `stepId` we invent, creating the step with exactly that value, so `syncSteps`
  resolves every key to an ID up front — reusing what state knows, minting
  `wfs_` + ULID for the rest (`plain/ids.go`) — and writes the whole graph,
  transitions included, in one call. There is no ID-discovery round trip and
  nothing depends on Plain returning results in input order. Verified against a
  live workspace; see `.docs/workflows.md` for the probe table.
- **An absent field and an explicit null are different to this API.**
  genqlient's `optional: pointer` emits pointers without `omitempty`, so a nil
  `stepId` went up as `"stepId": null` and was rejected with `stepId: Required`
  where omitting the key entirely would have worked. Steps always set an ID now,
  so the trap is moot there — but check the wire format before assuming a nil
  pointer means "unset" anywhere else.
- **The read-back after Create/Update must use the resolved key-to-ID map.**
  Using anything else keys the steps by Plain ID and Terraform rejects the apply
  as an inconsistent result.

## Conventions

- **terraform-plugin-framework** only. No SDKv2, and do not mix protocols.
- **genqlient** generates the API types. Write `.graphql` operation files in
  `plain/graphql/operations/` and run `mise run generate`. Never hand-edit
  `plain/generated.go`.
- Every resource implements `ImportState`. Plain IDs are opaque and prefixed
  (`wf_`, `lt_`, `tier_`), so a bare ID is a sufficient import address.
- Optional+Computed for anything the API defaults, so drift is not reported on
  values the practitioner never set.
- Diagnostics name the attribute and say what to do about it. Prefer
  `AddAttributeError` over `AddError` when a specific attribute is at fault.
- `docs/` is generated by tfplugindocs from schema descriptions and `examples/`.
  Fix the source, then regenerate.

## Testing

**Unit tests need no credentials** and cover everything that can be decided
without the API: schema shape, JSON normalization, transition arity, step-ID
minting, `graphChanged` vs `stepsContentChanged`, the Zod summarizer, and the
step-graph validation rules. `validateStepGraph` is deliberately a pure function
taking a step map rather than a `ValidateConfigRequest`, so the rules can be
table-tested directly instead of through framework plumbing.

**Acceptance tests** (`TF_ACC=1`, via `mise run testacc`) create and destroy real
objects in a real Plain workspace. Point `PLAIN_API_KEY` at a scratch workspace,
never a production one. Every test uses a randomized name and asserts
`CheckDestroy`, so a failed run does not silently leave objects behind.

**Never run two acceptance suites against one workspace at the same time.**
`mise run testacc` is serial within a run; two concurrent runs produced HTTP
500s from `deleteWorkflow` and orphaned real objects. And `CheckDestroy` only
runs after a *successful* destroy — a destroy that fails leaves the object
behind and reports nothing, so sweep for `tf-acc*` workflows after any failed
run.

The one that matters most is `TestAccWorkflow_publishLifecycle`. It is the only
thing that can catch a regression in the unpublish/republish sequencing, and it
asserts the behaviour in both directions:

- A payload-only edit must leave the workflow live for the whole apply.
- A rewired branch must drop it to draft, restructure, and republish.

Both halves are checked against Plain's `publishedAt`, not against the
`published` attribute — the attribute is a bool and reads `true` either way, so
a workflow that was briefly taken offline mid-apply looks identical to one that
never moved. The timestamp is the only evidence. If you widen `graphChanged`,
this test is what should stop you.

Note also `TestAccWorkflow_import`, which asserts the documented rekeying rather
than ignoring it: imported steps come back keyed by Plain step ID, and the check
verifies each key equals its step's own ID.

### Manual end-to-end runs

The acceptance suite drives the provider through terraform-plugin-testing, not
through the `terraform` binary. Before a release it is worth exercising the real
CLI against a real build, because that is the only thing that shows what a
practitioner actually sees — diagnostic wording and wrapping in particular,
which no `ExpectError` regex tells you.

```sh
mise run install                          # build into GOBIN
mise run dev-override                     # write .terraformrc-dev
export TF_CLI_CONFIG_FILE=$PWD/.terraformrc-dev
export PLAIN_API_KEY=...                  # scratch workspace

mkdir /tmp/plain-e2e && cd /tmp/plain-e2e # write a main.tf, then:
terraform apply
```

**Do not run `terraform init`** — it fails for a provider under `dev_overrides`,
by design. Skip it.

Worth walking through: `apply`, then `plan -detailed-exitcode` (must exit 0, no
drift), then `terraform import` into a fresh directory, then `destroy`. The
post-import plan showing an in-place update is correct, not a bug — that is the
step rekeying described in `examples/resources/plain_workflow/import.sh`.

Name anything created here `tf-acc*` so the same sweep finds it.

**`ImportStateVerify` cannot check a `jsontypes.Normalized` attribute**, and
this catches people. It compares state attributes as raw strings. `jsonencode()`
sorts object keys while Plain returns its own order, and after an apply the
framework's semantic equality deliberately keeps the *config-shaped* string in
state (`ValueSemanticEqualityString` sets `NewValue = priorValuable`) so the
difference never surfaces as drift. An import has no prior value to keep, so
Plain's shape lands instead — and a literal comparison then fails on two
equivalent values.

So `trigger` is in `ImportStateVerifyIgnore` and asserted by
`checkImportedTriggerIs`, which compares parsed JSON. Step payloads get the same
treatment via `checkImportedPayloads`, since `steps` is already ignored
wholesale for the rekeying and they would otherwise go unverified entirely. Any
new JSON attribute needs the same handling — ignoring it without adding a
semantic check silently drops it from the test.
